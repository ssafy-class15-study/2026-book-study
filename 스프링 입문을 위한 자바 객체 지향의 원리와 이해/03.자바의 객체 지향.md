# 3. 자바와 객체 지향

## 객체 지향은 인간 지향이다

- 프로그래밍 언어의 발전사
    - 기계 중심의 기계어 → 어셈블리어 → C, C++, Java
        - 로우 레벨의 기계가 아닌 인간을 배려하기 위한 과정
- 기존의 구조적 프로그래밍 언어에서 가장 중요한 것은 ‘함수’
    - 함수는 코드를 논리적인 단위로 구분하고 분할해서 정복하자는 의미
    - 아무리 복잡한 문제라도 작은 문제로 분할해서 하나씩 정복하다 보면 결국 해결(코드도 똑같이)

### 객체 지향

- 함수로 인해 프로그래밍이 편해지고 나서 파격적인 제안이 나옴 → 객체 지향
- 주위를 둘러보면 우주 만물은 **객체들의 합**이라는 것을 알 수 있음
    - 보이는 것, 만져지는 것, 상상되는 것 → 모든 것들은 사물
- 사물을 더 멋진 용어로 `객체(Object)` 라고 함.

### 클래스 객체 비유는 붕어빵틀과 붕어빵이 아니다.

- 보통 클래스와 객체의 관계를 붕어빵틀과 붕어빵으로 설명하곤 한다.

```java
붕어빵틀 붕어빵 = new 붕어빵틀(); //???
```

- 위 코드는 논리에 맞지 않다.
- 붕어빵틀을 생산하는 금형 기계가 있다고 하자. 그럼 같은 논리로 금형 기계는 붕어빵틀을 찍어내는 클래스가 된다.

```java
금형기계 붕어빵틀 = new 금형기계();
```

- 금형기계와 붕어빵틀이 클래스와 객체 관계가 아님.
- 그럼 붕어빵에게 붕어빵틀은 무엇인가? **붕어빵틀은 붕어빵을 만드는 공장(팩토리)**

- 사람, 김연아, 뽀로로, 펭귄은 각각 클래스인가? 객체인가?
    - 클래스와 객체를 구분하는 간단한 방법은 `나이`를 물어보는 것 → 사람과 펭귄

### 추상화와 T 메모리

- 모델링에서 가장 중요한 건 추상화 → 애플리케이션 경계 내에서 관심 있는 특성들만 가져다 사용하자. → 모델 → 자바에서 클래스
    - 표현법은 국제 표준 UML 클래스 다이어 그램.
- 어떤 클래스가 존재하면 그 클래스는 java.lang 패키지와 함께 T 메모리의 스태틱 영역에 배치된다.
    - 속성은 클래스에 속한게 아니라 객체에 속한 것이기 때문에. 메모리 공간이 스태틱 영역이 아닌 **힙 영역**에 할당된다.

### 클래스와 객체의 메모리 구조

- 클래스의 속성은 객체가 생성될 때마다 힙 영역에 개별적으로 할당됨
    - 각 객체는 독립적인 속성 값을 가지게 됨
    - 예: Mouse mickey = new Mouse(); 를 실행하면 mickey 객체의 속성들이 힙에 생성
- 클래스의 메서드는 스태틱 영역에 단 하나만 존재
    - 모든 객체가 공유해서 사용
    - 메모리 효율성을 위한 설계

<aside>

**객체 생성 시 T 메모리 변화**

1. 스태틱 영역: 클래스 정보와 메서드
2. 스택 영역: 객체 참조 변수
3. 힙 영역: 실제 객체의 속성들
</aside>

## 상속 : 재사용 + 확장

- 객체 지향에서의 상속은 상위 클래스의 특성을 하위 클래스에서 상속(특성 상속)하고, 거기에 더해 필요한 특성을 추가(확장)해서 사용할 수 있다는 의미
- 객체 지향의 상속은 재사용과 확장으로 이해해야 함
    - 부모-자식 관계가 아니라 분류 관계로 이해
    - 상위 클래스 - 하위 클래스 혹은 슈퍼 클래스 - 서브 클래스

### 상속의 is a 관계와 is kind of 관계

- is a 관계: "~은 ~이다"
    - 예: 펭귄 is a 동물 (펭귄은 동물이다)
    - 하위 클래스는 상위 클래스다 (O)
- is kind of 관계: "~은 ~의 한 종류이다"
    - 예: 펭귄 is kind of 조류 (펭귄은 조류의 한 종류다)
    - 더 명확한 표현

### 상속과 인터페이스

- 인터페이스는 "be able to" 관계
    - 예: Serializable 인터페이스 → 직렬화 할 수 있는
    - "~할 수 있는"의 의미
- 상속은 is a kind of 관계, 인터페이스는 be able to 관계로 구분

### 상속과 T 메모리

- 하위 클래스의 인스턴스가 생성될 때
    - 상위 클래스의 속성도 함께 힙 영역에 생성됨
    - 하위 클래스 인스턴스는 상위 클래스의 속성과 메서드를 모두 사용 가능

<aside>

**상속의 강력함**

하위 클래스는 상위 클래스의 특성을 물려받아 사용하면서, 추가로 자신만의 특성을 더할 수 있다.

</aside>

## 다형성 : 사용편의성

- 다형성이란 사용 편의성을 높이기 위한 것
- 오버라이딩(Overriding)과 오버로딩(Overloading)이 대표적

### 오버라이딩 (재정의)

- 상위 클래스의 메서드를 하위 클래스에서 같은 메서드 시그니처(이름, 파라미터)로 재정의하는 것
- 하위 클래스가 상위 클래스의 메서드를 자신에게 맞게 변경

<aside>

**오버라이딩 조건**

- 메서드 이름이 같아야 함
- 메서드 인자의 개수와 타입이 같아야 함
- 메서드 리턴 타입이 같아야 함
</aside>

### 오버로딩 (중복 정의)

- 같은 메서드 이름에 서로 다른 인자 목록을 가진 메서드를 여러 개 정의하는 것
- 메서드 이름은 같지만 인자 리스트가 다름
- 대표적 예: println() 메서드
    - println(int), println(String), println(double) 등

<aside>

**오버로딩 조건**

- 메서드 이름이 같아야 함
- 메서드 인자의 개수 또는 타입이 달라야 함
- 리턴 타입은 관계없음
</aside>

### 다형성과 T 메모리

- 상위 클래스 타입의 객체 참조 변수를 사용하더라도 하위 클래스의 오버라이딩된 메서드가 호출됨

```java
동물 뽀로로 = new 펭귄();
뽀로로.날다(); // 펭귄의 날다() 메서드가 호출됨
```

## 캡슐화 : 정보 은닉

- 객체의 속성과 메서드를 하나로 묶고, 실제 구현 내용을 외부에 감추는 것
- 접근 제어자를 통해 구현
    - public: 모두 접근 가능
    - protected: 상속 관계 또는 같은 패키지 내에서 접근 가능
- default (package-private): 같은 패키지 내에서만 접근 가능
- private: 해당 클래스 내에서만 접근 가능
- 캡슐화의 장점
    - 객체의 내부 구현을 숨기고 외부에는 필요한 기능만 제공
    - 코드의 유지보수성과 재사용성 향상
    - 객체 간의 결합도를 낮춤

<aside>

**정보 은닉의 핵심**

속성은 private으로 선언하고, getter/setter 메서드를 통해 접근하도록 하는 것이 일반적인 캡슐화 패턴

</aside>

### 접근 제어자 정리

| **접근 제어자** | **클래스 내부** | **같은 패키지** | **상속 받은 클래스** | **외부** |
| --- | --- | --- | --- | --- |
| private | O | X | X | X |
| default | O | O | X | X |
| protected | O | O | O | X |
| public | O | O | O | O |
