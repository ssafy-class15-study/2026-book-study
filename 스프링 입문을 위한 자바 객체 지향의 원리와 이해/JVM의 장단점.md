## JVM은 무조건 좋은 걸까?

자바는 Write once, run anywhere라는 말처럼 플랫폼(실행 환경)에 독립적인 언어로 유명하다.  
이렇게 할 수 있는 이유는 JDK - JRE - JVM의 구조로 이루어진 자바 어플리케이션의 실행 구조 덕분인데 

자바 파일 실행 순서는 다음과 같다. 

```java
.java (소스 코드)
   ↓  JDK의 javac (컴파일)
.class (바이트코드)
   ↓  JVM
기계어로 변환 + 실행
```

+ JDK = 개발 도구 모음 (컴파일러 포함) -> .java 파일을 .class 파일로 변환해줌 
+ JRE = JVM + 실행에 필요한 라이브러리
+ JVM = 바이트코드를 실제 OS/CPU에서 돌리도록 변환


**컴파일러와 인터프리터란?**  
컴파일러: 소스 코드를 한 번에 다른 코드로 번역해두는 것 
+ 즉 .java -> .class
+ 자바에서는 javac라는 컴파일러가 수행함 
인터프리터: 코드를 한줄 씩 읽으면서 바로 실행하는 방식

자바는 특이하게 컴파일러와 인터프리터를 함께 실행한다.  
처음 실행할 때는 바이트 코드르 한 줄 씩 읽으면서 실행한다 (인터프리터 방식)  
자주 실행되는 코드가 있으면 이 부분을 기계어로 다시 번역해서 캐싱해둔다.  
이걸 JIT(Just In Time) 컴파일이라고 부른다.

여기서 내가 생긴 궁금증은 그럼 javac가 처음에 .java 파일을 .class 파일로 변경하는 작업은 뭔데?    
1. 자바에서는 컴파일이 두번 일어난다.1. 처음 javac가 .java 파일을 .class 로 변경하는 단계
+ 사람이 작성한 소스 코드를 JVM 이해하는 바이트코드로 바꾸는 단계임 
2. JVM 안에서 인터프리터 혹은 컴파일이 이루어짐
+ .class 파일을 CPU가 바로 읽을 수 있는게 아님 그래서 JVM이 CPU가 바이트 코드를 읽을 수 있게 변경하는데 이 때 처음에는 바이트코드를 한 줄씩 읽고 기계어로 변경해줌, 그런데 계속 반복되는 코드를 발견하면 그 부분을 통째로 기계어로 번역해서 저장해둔다.



> 자바 프로그램이 실행되는 과정은 확실히 C 언어에 비해서 무거운 과정임
+ 프로그램을 실행하기 전에 컴파일 과정 수행, 클래스 로딩 과정 수행, 검즈과정, JIT 컴파일, 런타임 최적화 등의 과정을 거치기 때문.
+ 하지만 JIM과 같은 최적화 덕분에 실행 속도 문제가 느린 부분을 상당 부분 해결할 수 있음 
  
자바 프로그램 실행 구조의 장점
+ 이식성
+ 자동 메모리 관리
+ 런타임 최적화

단점
+ 초기 실행 느림
  + JVM 뜨는 시간 필요.
+ 메모리 많이 사용
  + 런타임이 무겁다. -> 대신 GC 덕분에 메모리 안정싱이 올라감 


> 자바는 메모리를 조금 더 쓰더라도 예측 가능하고 안전하게 동작하는 것을 더 중요시 하는 언어이다.  

자바에서 사용하는 pool 또한 JVM이 효율성과 안정성을 얻기 위해 선택한 캐싱 전략이다.
+ String Pool
+ Constant Pool
+ Thread Pool
+ Connection Pool

이렇게 자바에는 유독 Pool이라는게 많은데 Pool은 미리 만들어두고 공유해서 재사용하기 위한 저장공간과 같은 같은 개념이다.
+ 중복 생성을 막고
+ 메모리를 아끼고
+ 속도를 빠르게 하기 위함인데

자바는 객체 지향 언어이기에 클래스르 만들고, 관리하는데 생각보다 많은 메모리 오버헤드가 발생하게 된다.  
그래서 자주 사용하게 되는 문자열과 같은 객체들을 매번 새로 생성하지 않고 만들어둔 것을 재사용하는 방법을 선택하게 된 것이다.  
이런 Pool 정보들은 특정 객체가 소유하는 개념이 아니라 클래스 전체가 공유하는 정보이기 때문에 스택이나 힙 영역이 아니라 메서드 영역에 클래스 메타 정보와 함께 올라가는 것이다.  

Pool이라는게 처음에 따로 만들어서 메모리 영역에 올리니까 시작 부터 메모리를 더 사용한다고 생각할 수 있지만, 자바 언어 자체가 오래 실행되고, 많이 반복되는 프로그램을 기준으로 설계되었기 때문에 이런 방식을 선택한 것이다.

따라서 풀(Pool)은 초기 메모리를 더 사용하는 전략처럼 보이지만, 장기적으로는 객체 생성과 GC 비용을 줄여  전체 시스템의 안정성과 성능을 향상시키는 구조이다.


### 결론 
자바의 JVM은 메모리를 더 사용하고 실행 속도 역시 C 언어에 비해 느릴 수 있기 때문에 언제나 최고의 선택이라고 말하기는 어렵다.  
그러나 자바가 처음부터 추구했던 목표를 생각해 보면, 그 목적에 부합하는 환경에서는 오히려 매우 강력하고 안정적인 실행 환경을 제공한다고 볼 수 있다.  
자바가 오랜 시간이 지난 지금까지도 꾸준히 선택받는 이유는 바로 이러한 설계 철학 덕분이라고 생각한다.

자바가 추구한 핵심 목적은 플랫폼에 독립적인 실행 환경, 안정성, 그리고 대규모 시스템에서도 유지보수가 가능한 구조였다.  
운영체제가 달라도 동일하게 동작해야 했고, 개발자의 실수를 런타임에서 최대한 보호하며, 오랜 기간 서비스가 운영되더라도 예측 가능한 동작을 보장하는 것이 중요했다.  
JVM, 바이트코드, 가비지 컬렉션, 그리고 다양한 풀 전략은 모두 이러한 목표를 달성하기 위한 선택들이라고 볼 수 있다.
