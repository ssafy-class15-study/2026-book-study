# 05. 객체 지향 설계 5원칙 - SOLID

- **S**RP (Single Responsibility Principle) : 단일 책임 원칙
- **O**CP (Open Closed Principle) : 개방 폐쇄 원칙
- **L**SP (Liskov Substitution Principle) : 리스코프 치환 원칙
- **I**SP (Interface Segregation Principle) : 인터페이스 분리 원칙
- **D**IP (Dependency Inversion Principle) : 의존 역전 원칙

이 원칙은 높은 응집도(High Cohesion), 낮은 결합도(Loose Coupling)의 고전원칙을 객체 지향의 관점에서 재정립한 것

SOLID는 개념이기에 보는 관점에 따라 다르게 해석될 수 있다.

하지만 우리가 만드는 소프트웨어에 녹여내야 한다. SOLID를 잘 녹여낸 소프트웨어는 상대적으로 이해하기 쉽고, 논리적으로 정연하며, 리팩토링 및 유지보수가 수월하다.

SOLID는 디자인 패턴의 뼈대이며 스프링 프레임워크의 근간이다.

아래 내용은 SOLID의 가장 단순한 예제이며, SOLID의 더 많은 내용은 [클린 소프트웨어](https://product.kyobobook.co.kr/detail/S000001875106) - [ Part 2 애자일 설계 ], [UML 실전에서는 이것만 쓴다](https://product.kyobobook.co.kr/detail/S000001469868) - [6장 객체 지향 개발의 원칙] 을 읽어보면 도움된다.

### SRP - 단일 책임 원칙

<img width="929" height="507" alt="Image" src="https://github.com/user-attachments/assets/d5412183-8482-409e-9f22-fbe7f8934338" />

위와 같이 남자라고 하는 클래스와 남자 클래스에 의존하는 다양한 클래스가 있다고 생각해보자.

남자의 역할과 책임이 너무 많다. 

객체 지향에선 이런 경우를 나쁜 냄새가 난다고 한다. 역할을 분리하는 것이 단일 책임 원칙.

<img width="1903" height="635" alt="Image" src="https://github.com/user-attachments/assets/ddf86e66-f0d2-4938-85d2-b98d30e75a5e" />

남자라는 하나의 클래스가 역할과 책임에 따라 네 개의 클래스로 쪼개졌다. 역할과 클래스명도 서로 일치하니, 이해하기도 좋다. 이제 회사를 퇴사하더라도 다른 관계들은 아무런 형향을 받지 않는다.

단일 책임 원칙은 속성, 메서드, 패키지, 모듈, 컴포넌트, 프레임워크 등에도 적용할 수 있다.

---

단일 책임 원칙은 잘된 경우보다 잘못된 경우를 살펴볼 때 이해하기 좋다.

여성은 절대로 군대를 가지 않는 세계가 있다고 가정하자

```jsx
class Person {
	String milNum // 군번
	...
}

...

Person romeo = new Person();
Person juliet = new Person();
```

Person 참조 변수 줄리엣이 가진 군번 속성에 값을 할당하거나 읽어 오는 코드를 막을 방법이 없다. 냄새나는 코드

Person 클래스를 남자 클래스와 여자 클래스로 분할하고, 남자 클래스에만 군번 속성을 갖게 하면 향기나는 코드

남자 클래스와 여자 클래스에 공통점이 없다면 사람 클래스는 제거. 공통점이 많다면, 사람 클래스를 상속후 차이점만 구현하면 된다.

> 속성이 SRP를 지키지 못하는 경우
> 

하나의 속성이 여러 의미를 갖는 경우도 단일 책임 원칙을 지키지 못하는 경우이다.

DB에서 하나의 필드가 토지일 경우 면적을, 건물인 경우 층수를 나타내는 경우. 냄새나는 속성이다.. DB 설계할 때 정규화가 확장해서 생각하면 단일 책임 원칙을 적용하는 것

> 메서드가 SRP를 지키지 못하는 경우
> 

```jsx
class Dog {
	final static boolean male = true;
	final static boolean female = false;
	boolean gender;
	
	void pee() {
		if(this.gender == male) {
			// 한 쪽 다리를 들고 소변보다.
		} else {
			// 뒷 다리 두 개를 굽혀 앉은 자세로 소변보다.
		}
	}
}
```

강아지가 수컷이냐 암컷이냐에 따라 pee() 메서드에서 분기 처리가 진행된다. pee() 메서드가 수컷 강아지의 행위와 암컷 강아지의 행위를 모두 구현하려고 하기에 SRP 위배

메서드가 단일 책임 원칙을 지키지 않는 경우 나타나는 대표적인 냄새가 분기 처리를 위한 if문이다.

```jsx
abstract class Dog {
	abstract void pee();
}

class MaleDog extends Dog {
	void pee() {
		// 한쪽 다리
	}
}

class FemaleDog extends Dog {
	void pee() {
		// 뒷 다리 두 개
	}
}
```

위와 같이 분리하면 좋다.

### OCP - 개방 폐쇄 원칙

자신의 확장에는 열려 있고, 주변의 변화에 대해서는 닫혀 있다.

<img width="929" height="600" alt="Image" src="https://github.com/user-attachments/assets/ae306ad5-8bc5-4b39-b2f7-f8d8d551c008" />

운전자가 마티즈를 구입해서, 열심히 마티즈에 적응했다. 그리고 몇 년 뒤 운전자가 쏘나타가 생겼다.

창문과 기어가 수동이던 마티즈에서, 창문과 기어가 자동인 쏘나타로 차종을 바꾸니, 운전자의 행동에도 변화가 온다.

현실 세계에선 차량의 변경으로 운전자에게 어느정도 변화가 있어야 하겠지만, 객체 지향 세계에선 다른 해법이 있다.

<img width="1216" height="707" alt="Image" src="https://github.com/user-attachments/assets/03f4e6f1-65a1-4e2d-ba55-00d76c5549e9" />

위와 같이 상위 클래스 or 인터페이스를 중간에 두며 다양한 자동차가 생긴다고 해도, 객체 지향 세계의 운전자는 습관에 영향을 받지 않게 된다. 다양한 자동차가 생긴다고 하는 것은 자동차 입장에서는 자신의 확장엔 개방돼 있는 것이고, 운전자 입장에는 주변의 변화에 폐쇄돼 있는 것이다.

JDBC가 개방 폐쇄 원칙의 아주 좋은 예.

JDBC를 사용하는 클라이언트는 DB를 오라클에서 MySQL로 바꾸더라도 Connection을 설정하는 부분 외엔 따로 수정할 필요가 없다.

오라클에서 MySQL이나 MS-SQL로 교체할 때, JDBC 인터페이스라는 완충 장치로 변화에 영향을 받지 않는다.

자바 애플리케이션은 데이터베이스라고 하는 주변의 변화에 닫혀있는 것.

데이터베이스는 자신의 확장에 열려있다는 것

자바에도 개방 폐쇄 원칙이 적용돼 있다.

개발자는 소스코드가 윈도우 리눅스등 다른 운영체제에서 구동될지에 관해선 걱정하지 않는다.

각 운영체제별 JVM과 목적 파일이 있기때문.

즉 소스코드는 운영체제의 변화에 닫혀있는 것.

JVM은 확장에 열려있는 것.

소스코드와 운영체제별 JVM 사이에는 목적 파일이라는 완충 장치가 있는 것이다.

이 외에도 자바 내의 상속 구조를 통해서도 개방 폐쇄 원칙을 확인 가능하다.

Number의 상속 관계랑 InputStream의 상속 관계만 뜯어봐도 OCP를 음미할 수 있다.

개방 폐쇄 원칙을 무시한다고 객체지향 프로그램을 구현 못하는 건 아니지만, 유연성, 재사용성, 유지보수성이 불가능해진다.

→ 개방 폐쇄 원칙은 반드시 지켜야하는 원칙이다.

스프링 프레임워크는 개방 폐쇄 원칙을 교과서적으로 활용하고 있다.

### LSP - 리스코프 치환 원칙

서브 타입은 언제나 자신의 기본 타입으로 교체할 수 있어야한다.

전에 말했듯, 상속은 조직도나 계층도가 아닌 분류도다.

- 하위 클래스 is a kind of 상위 클래스 - 하위 분류는 상위 분류의 한 종류다.
- 구현 클래스 is able to 인터페이스 - 구현 분류는 인터페이스할 수 있어야 한다.

위 문장대로 구현된 프로그램이라면 이미 LSP를 지키고 있다.

하지만 상속이 조직도나 계층도 형태로 구축된 경우, LSP가 위배되고 있다는 것

아버지를 상위 클래스로 하는 딸이 있다고 하자. 이는 전형적인 계층도 형태이며 상속을 잘못 적용한 예이다.

`아버지 춘향이 = new 딸()`

춘양이는 아버지형 객체 참조 변수로, 아버지가 가진 행위를 할 수 있어야 하지만, 춘향이에겐 아버지의 행위를 시키지 못한다.

반면, `동물 뽀로로 = new 펭귄()` 논리적으로 완벽하다.

서브 타입은 언제나 자신의 기본 타입으로 교체할 수 있어야한다.

→ 하위 클래스의 인스턴스는 상위형 객체 참조 변수에 대입해 상위 클래스의 인스턴스 역할을 하는 데에 문제가 없어야 한다.

하위에 존재하는 것들은 상위에 있는 것들의 역할을 하는 데 전혀 문제가 없어야 하는 것

- 하위형에서 선행 조건은 강화될 수 없다.
- 하위형에서 후행 조건은 약화될 수 없다.
- 하위형에서 상위형의 불변 조건은 반드시 유지돼야 한다.

### ISP - 인터페이스 분리 원칙

클라이언트는 자신이 사용하지 않는 메서드에 의존 관계를 맺으면 안된다.

SRP에서 남자 클래스를 단일 책임을 가진 여러 클래스로 분리했다. 근데 남자를 다수 클래스로 분리하는 방법만이 있는 게 아니다. 

다른 방법이 바로 ISP를  사용하는 것

<img width="1008" height="404" alt="Image" src="https://github.com/user-attachments/assets/f015cca3-3e5b-444f-b00b-1395801d3663" />

남자 클래스를 역할에 맞는 인터페이스를 만들어, 각각의 역할에 맞는 인터페이스로 제한하는 것이 ISP이다.

SRP와 ISP는 같은 문제에 대한 두 가지 다른 해법이다.

SRP는 응집도 향상, ISP는 결합도 감소를 일으킨다. 설계자의 취향에 따라 둘 중 하나를 선택해서 설계가능하지만, 특별한 경우가 아니라면 SRP가 더 좋은 해결책이다.

ISP와 항상 함께 등장하는 원칙. 

> **인터페이스 최소주의 원칙**
> 

인터페이스를 통해 메서드를 외부에 제공할 때는 최소한의 메서드만 제공해야 한다.

상위 클래스는 풍성할수록 좋고, 인터페이스는 작을수록 좋다.

빈약한 상위 클래스를 사용하게 되면 여기저기 형변환이 발생하면서 상속의 혜택을 제대로 누리지 못한다.

풍성한 상위 클래스를 이용하는 경우, 사용 불가능한 경우나 불필요한 형변환이 없어진다.

인터페이스 최소주의

- 그 역할에 충실한 최소한의 기능만 공개하는 것

### DIP - 의존 역전 원칙

> 고차원 모듈은 저차원 모듈에 의존하면 안된다.이 두 모듈 모두 다른 추상화된 것에 의존해야 한다.
> 

> 추상화된 것은 구체적인 것에 의존하면 안된다. 구체적인 것이 추상화 된 것에 의존해야 한다.
> 

> 자주 변경되는 구체(Concrete) 클래스에 의존하지 마라.
> 

<img width="1096" height="222" alt="Image" src="https://github.com/user-attachments/assets/dfd75ee4-30ed-466d-a027-342b4f073700" />

자동차와 스노우타이어 사이엔 위와 같은 의존 관계가 있다.

자동차는 타이어보다 더 자주 변하는 스노우타이어에 의존한다. 냄새나는 코드.

<img width="974" height="390" alt="Image" src="https://github.com/user-attachments/assets/81ed5d2c-d200-4b7b-9e16-96bc09030fde" />

위와 같이 추상화된 타이어 인터페이스에만 의존하게 하여, 다른 타이어로 변경돼도 자동차는 이제 그 영향을 받지 않는 형태가 된다.

OCP에서 비슷하게 설명했던 내용이다. 상속과 다형성이니 결국 비슷비슷한 모습의 코드로 구현되며 유사성이 생긴다.

의존 역전 원칙에서 중요한 것은 스노우 타이어는 그 무엇에도 의존하지 않는 클래스였는데, 본인보다 추상적인 것인 타이어 인터페이스에 의존하게 된 것.

의존의 방향이 역전된 것이다. 자동자는 본인보다 자주 변하는 스노우 타이어에 의존하는 관계였는데, 중간에 추상화된 타이어 인터페이스를 추가해, 의존 관계가 역전되고 있다.

즉 A → B 관계였던 것이 A → Interface ← B가 된 것.

자신보다 변하기 쉬운 것에 의존하지 마라

하위 클래스나 구체 클래스보다 상위 클래스일수록, 인터페이스일수록, 추상 클래스일수록 변하지 않을 가능성이 높기에 이를 의존하라는 것이 DIP이다.

### 정리

봐왔지만, SOLID는 갑자기 생긴 것이 아닌 객체 지향 4대 특성을 제대로 활용한 결과로 당연히 나타나는 것

→ 객체지향 4대 특성을 제대로 이해해야 SOLID를 제대로 이해하고 활용할 수 있다.

SOLID를 이야기할 때 빼놓을 수 없는 게 SoC(관심사의 분리)이다.

SoC

- 관심이 같은 것끼리는 하나의 객체 안으로 or 친한 객체로 모으고
- 관심이 다른 것은 가능한 한 따로 떨어져 서로 영향을 주지 않도록 분리
- 하나의 속성, 하나의 메서드, 하나의 클래스, 하나의 모듈, 하나의 패키지엔 하나의 관심사만 들어있어야 한다.

SoC를 적용하면 자연스럽게 SRP, ISP, OCP에 도달하게 된다.

스프링 또한 SoC를 통해 SOLID를 극한까지 닦았다.

정리

- SRP : 어떤 클래스를 변경해야 하는 이유는 오직 하나뿐이어야 한다.
- OCP : 자신의 확장에는 열려 있고, 주변의 변화에 대해서는 닫혀 있어야 한다.
- LSP : 서브 타입은 언제나 자신의 기반 타입으로 교체할 수 있어야 한다.
- ISP : 클라이언트는 자신이 사용하지 않는 메서드에 의존 관계를 맺으면 안 된다.
- DIP : 자신보다 변하기 쉬운 것에 의존하지 마라

SOLID를 적용하면 소스파일의 개수가 더 많아지는 경향이 있다. 이렇게 많아진 파일이 논리를 더 잘 분할하고, 잘 표현하기에 직관적이고 유지관리 및 보수가 쉬운 소스가 만들어진다.

객체 지향 특성과 설계 원칙과 디자인 패턴에 대한 이해는 스프링 프레임워크를 이해하기 위해 반드시 필요한 것.
